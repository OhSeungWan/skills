# qa

트랙 하나의 QA를 노션 **QA 시트** 한 장으로 돈다. 사람이 항목을 쌓고, agent가 재현·수정해 **배치** PR을 내고, 사람이 **team 존**에서 눈으로 확인해 닫는다.

```
작성 중 ──사람이 제출──> 시작전 ──집어듦──> 진행 중 ──배치 PR──> 리뷰 ──머지 감지──> PR 완료
                          ^            │                                          │
                          │            └──원인 미특정 · 스펙대로 · 보류──> 사람 확인 필요
                          │                                                       │
                          └──────────────사람이 정보 보강─────────────────────────┘

PR 완료 ──team 존에서 사람 눈──> 배포 완료
```

**agent가 관측할 수 없는 것만 사람이 찍는다** — 다 썼다는 의사(`시작전`)와 눈으로 봤다는 판정(`배포 완료`) 둘뿐이다. 나머지 전이는 전부 관측 가능한 사실이라 agent가 찍는다. 관측으로 알 수 있는 걸 사람에게 시키면 그 칸은 영원히 비어 있다.

**큐 조건은 `시작전` 정확히 하나다.** `작성 중`도, 상태가 빈 행도 집지 않는다 — 사람이 노션에서 타이핑하는 중인 행을 agent가 집어들면 미완성 정보로 엉뚱한 걸 고친다.

## 값 결정 (두 분기 공통, 맨 먼저)

| 값 | 결정 방법 |
| --- | --- |
| QA 시트 | 인자로 받은 노션 DB URL이 1순위, 다음이 repo 관례 문서(`CLAUDE.md` · `docs/agents/qa.md` 류), 없으면 트랙명·브랜치명으로 워크스페이스 검색 후 **후보를 제시하고 확인받는다** |
| 시트 부모 페이지 | 시트가 없어 새로 만들 때만 필요하다. 위치는 추론하지 않고 URL을 묻는다 — 노션에 잘못 만든 DB는 사람 손으로만 지운다. 받은 URL은 관례 문서에 적어 다음부터 안 묻는다 |
| 통합 브랜치 · 통합 PR | `track` 스킬의 값 결정 표를 따른다 |
| team 존 | 통합 브랜치가 배포되는 환경. 사람이 수정 결과를 눈으로 보는 유일한 자리다 |
| 스펙 이슈 | ②에서만 쓴다. 통합 PR 본문과 티켓 이슈의 참조에서 찾고, 없으면 트랙명·화면 이름으로 `gh issue search`. 그래도 없으면 **없는 채로 진행한다** — 스펙은 판정을 강화하는 근거지 수정의 전제가 아니다 |

## 시트 스키마

| 프로퍼티 | 타입 | 채우는 주체 |
| --- | --- | --- |
| (title) | title | agent — 증상 요약 한 줄. 새로 만드는 시트는 이름을 `증상`으로, 기존 시트는 이름이 무엇이든 그대로 두고 거기에 증상을 쓴다 |
| 테스트 번호 | number | agent — 시트 내 최대 + 1 |
| 재현순서 | text | 사람 |
| 테스트한 사람 | person | 사람 |
| 성질 | select `폴리싱` / `로직` / `미판정` | agent |
| 해결 여부 | status — 위 상태 머신 7개 | agent (`시작전`·`배포 완료`는 사람) |
| PR | url | agent |
| 비고 | text | agent — `사람 확인 필요`로 보낼 때 사유 |

기존 시트를 만나면 **없는 프로퍼티와 없는 status 옵션만 추가한다**(`notion-update-data-source`). status 옵션 추가는 기존 행의 값을 건드리지 않는다. status 그룹은 `작성 중`·`시작전`·`사람 확인 필요`를 to-do, `진행 중`·`리뷰`·`PR 완료`를 in-progress, `배포 완료`를 complete에 둔다 — 사람 눈을 통과하기 전은 끝난 게 아니다. `작성 중`을 to-do의 맨 앞에 둬서 노션이 새 행에 먼저 제안하게 한다.

## 분기 판별

인자가 `collect`/`fix`면 그 분기로 간다. 인자가 없으면 시트의 상태 분포를 읽고 "지금은 ②로 보인다 — 맞나?"라고 **묻고 시작한다.** 두 분기 모두 외부에 보이는 것(노션 행·브랜치·PR)을 만든다.

## ① collect — 러프한 보고를 항목으로 쌓기

팀원이 QA 세션에서 발견한 걸 터미널에 통째로 붙여넣는다. 형식은 없다. 슬랙·노션 코멘트를 감시하지 않는다 — 입력 채널은 이 하나다.

절차:

1. QA 시트를 찾는다. 없으면 부모 페이지 URL을 묻고 위 스키마로 생성한다.
2. 붙여넣은 덩어리를 항목 단위로 쪼갠다. 한 줄에 여러 결함이 섞여 있으면 나눈다.
3. **재현순서가 없는 항목은 그 자리에서 한 번 되묻는다.** 여기가 되물을 수 있는 유일한 순간이다 — 되묻는 이유는 재현이 아니라 **화면과 조건을 특정**하기 위해서다. agent는 ②에서 코드로 원인을 짚는데, 어느 화면 어느 조건인지 없으면 코드에서 출발점을 못 잡는다. 여기서 못 받으면 그때는 QA 세션이 이미 끝나 있다.
4. 행을 만들고 상태를 **`시작전`으로** 둔다 — 붙여넣는 행위가 곧 제출이라 `작성 중`을 거치지 않는다. 되물어도 재현순서를 못 받은 항목만 `재현순서: 미제공`으로 쌓고 `사람 확인 필요`로 시작한다.
5. `성질`을 판정해 채운다. 문구·간격·색·오타처럼 로직에 손대지 않는 것이 `폴리싱`, 나머지가 `로직`, 보고만으로 못 가르면 `미판정`.

중복 판정은 하지 않는다. 제목 유사도 판정은 오탐이 잦고, 중복은 사람이 시트를 보면 보인다.

완료 기준: 붙여넣은 보고의 모든 항목이 행으로 존재하고, 각 행에 `성질`과 상태가 채워져 있다.

## ② fix — 쌓인 항목 처리

**실행 1회 = 배치 1개.** PR 하나가 열리면 사람이 볼 게 생기고 그 사이 코드가 움직이므로, 다음 배치는 다음 실행에서 판단한다.

**판정: 통합 PR이 열려 있는가.** 열려 있을 때만 진행한다. 닫혀 있으면 수정 결과를 team 존에서 확인할 방법이 없어 `배포 완료`가 영원히 안 찍히고 시트가 좀비가 된다. 그 경우 "이 트랙은 QA 루프가 끝났다 — 새 항목은 새 트랙이나 핫픽스로" 라고 보고하고 멈춘다.

절차:

1. **동기화.** 열린 배치 PR의 머지 여부를 확인해 `리뷰` → `PR 완료`로 갱신한다. `진행 중`인데 `PR`이 빈 항목은 죽은 실행이 남긴 **좀비**다 — `시작전`으로 되돌린다. `작성 중`이거나 상태가 빈 행이 있으면 **건드리지 말고 건수만 보고한다** — 쓴 사람이 제출을 잊었을 뿐일 수 있고, 그 리마인드가 여기 말고는 없다.
2. **배치 선정.** `시작전` 중 `폴리싱`이 있으면 그 전부가 배치 하나다(접점 무시). 없으면 `로직`을 **화면 이름**으로 묶는다 — 항목 제목과 재현순서에 적힌 화면으로 가르고, `테스트 번호`가 가장 작은 그룹을 고른다. 원인 파일로 묶지 않는다: 리뷰어가 느끼는 맥락은 파일이 아니라 화면이고, 파일로 묶으려면 버려질 원인분석을 먼저 해야 한다. 한 배치 상한은 항목 10장.

   **배치를 정했으면 그 화면의 스펙 컨텍스트를 먼저 읽는다.** 트랙 대시보드 티켓 표에서 배치 화면에 걸리는 티켓을 골라, 티켓 이슈와 거기 참조된 스펙 이슈를 읽는다 — 티켓도 화면 단위 vertical slice라 배치와 축이 같아서 그대로 매칭된다. 스펙 이슈의 Figma 링크·API 계약·구현 결정이 이 배치에서 "무엇이 맞는지"다. 해당 영역의 `CONTEXT.md`와 ADR도 같이 읽는다. 하나도 못 찾으면 못 찾은 채로 간다.
3. 배치의 항목을 `진행 중`으로 바꾼다.
4. **항목마다 코드에서 원인을 짚는다 — 앱을 띄워 따라 하지 않는다.** 재현순서에 적힌 화면·조건을 출발점으로 코드를 따라가 `file:line`과 "왜 이 증상이 나오는지" 한 줄을 근거로 남긴다. **짚기 전에 가설을 3~5개 적고 순위를 매긴다** — 각 가설은 "X가 원인이면 Y를 바꿨을 때 증상이 사라진다" 꼴로 반증 가능해야 하고, 순위 1번부터 코드로 검증한다. 하나만 떠올리면 처음 그럴듯한 것에 닻을 내려 엉뚱한 데를 고친다. 근거가 잡힌 항목만 고친다. 실행하지 않는 이유: E2E가 죽어 있어 실제로 재현하려면 매번 일회용 하네스(`repro.mjs` 류)를 짓게 되고, 그 하네스 짓는 비용이 버그보다 크다. "코드가 이렇게 동작하도록 쓰여 있다"는 재현보다 강한 근거다.

   - `성질`이 `폴리싱`이면 문자열·스타일이 있는 위치만 확인하고 고친다. 폴리싱은 team 존 사람 눈이 빠짐없이 잡는 종류라 그 이상 파는 건 중복이다. **스펙 이슈에 Figma 링크가 있으면 목표값을 반드시 대조한다 — 값이 다르면 Figma가 진실이다.** QA 보고는 "간격 좀 넓혀줘"까지고 목표값이 없어서, 대조 없이 고치면 사람 눈이 또 반려한다. 그 왕복이 폴리싱을 얕게 파서 아낀 이득을 도로 먹는다.
   - `미판정`이면 추적하는 과정에서 갈린다 — 코드를 짚어 보면 로직에 손대는지 아닌지 드러난다. 판정 결과를 `성질`에 쓴다.
   - 순수 계산·조건·상태 전이 항목은 실패하는 테스트 하나를 먼저 짜서 red를 확인하고 고쳐 green으로 만든다. UI 결함에는 테스트를 짜지 않는다 — 일회용 하네스와 같은 함정이다.
   - **코드에서 경로를 못 찾을 때만 실행·재현을 허용한다.** 기본값이 아니라 마지막 수단이고 게이트는 "정적 추적 실패" 하나뿐이다. 이때 만든 하네스는 리포 밖 임시 디렉터리에 두고 **커밋하지 않는다** — 같은 하네스가 반복해서 필요하면 그건 E2E를 되살릴 신호지 이 스킬의 일이 아니다.
   - 그래도 원인이 안 잡히면 `사람 확인 필요`로 보내고 `비고`에 무엇을 짚었고 어디서 끊겼는지 쓰고 `테스트한 사람`을 멘션한다 — 추정으로 고치면 새 버그를 낳는데 원 항목은 살아 있어서 사람 확인 때 또 터진다.
   - 스펙대로 동작하는 것으로 보이면 코드 근거를 `비고`에 적어 `사람 확인 필요`로 되돌린다. **관례 문서가 이 트랙의 정답지(오라클)를 지정하면 해당 항목 ID를 `비고`에 인용하고, 구현이 맞고 정답지가 틀린 것으로 판정되면 지정된 갱신 스킬로 정답지를 먼저 고친다** — 정답지를 안 고치면 다음 QA가 같은 항목을 또 버그로 보고한다. **스펙 이슈나 ADR에 근거가 있으면 링크를 함께 적고, ADR과 정면으로 어긋나면 그 사실을 그대로 쓴다** — agent 주장뿐인 판정은 사람이 뒤집기 쉽고, 뒤집히면 그 항목은 왕복만 한 셈이다. 이 판정에도 재현을 요구하지 않는다 — 사람이 반박하면 그때 재현한다.
5. 수정 커밋. 파일 15개를 넘으면 배치를 쪼갠다.
6. 검증은 타입체크·빌드·기존 테스트까지다. **변경한 파일에 걸리는 기존 테스트는 반드시 돌린다** — 실행으로 확인한 것이 없으니 이게 유일한 자동 안전망이다. E2E는 현재 죽어 있고, 최종 판정은 사람 눈이다.
7. 티켓 브랜치를 따고 통합 브랜치로 PR을 연다 — 브랜치 생성과 PR 개설 절차는 `track` ②를 그대로 쓴다. 본문은 **QA 항목 표**(테스트 번호 · 증상 · 노션 링크 · 원인 `file:line` 한 줄)와 **team 존에서 확인할 것** 목록, 그리고 맨 위에 `실행 검증 없음 — 정적 근거로 수정` 한 줄. **읽은 스펙 이슈가 있으면 그 링크를, 없으면 `스펙 근거 없음` 한 줄을 그 옆에 둔다.** 리뷰어가 무엇을 믿고 봐야 하는지 알아야 team 존 확인이 형식적으로 끝나지 않는다. 재현까지 갔던 항목은 그 항목만 표에 표시한다.
8. 배치 항목을 `리뷰`로 바꾸고 `PR`을 채운다. 항목마다 코멘트 하나 — 원인과 고친 방법, 2~3줄. 길게 쓰면 안 읽히고, 안 읽히는 코멘트는 `배포 완료`가 안 찍히는 원인이 된다.
9. 통합 PR 대시보드의 `배포 전 사람 몫` 블록에 QA 한 줄을 갱신한다 — QA 시트 링크 · `사람 확인 필요` 수 · `배포 완료`가 아직 아닌 수. 티켓 표에는 넣지 않는다: 티켓 표는 트랙 분할 계획의 산물이고 QA 배치는 계획에 없던 것이라, 섞이면 표가 계획인지 로그인지 모호해진다.

완료 기준: 배치 PR 하나가 통합 브랜치를 base로 열려 있고, 배치의 모든 항목이 `리뷰` 아니면 `사람 확인 필요`이며, **고친 항목마다 원인 근거(`file:line` + 한 줄)가 남아 있고**, 통합 PR 대시보드의 QA 줄이 갱신돼 있다. 근거 없이 고친 항목이 섞이면 이 설계는 조용히 예전으로 돌아간다.

## 승인과 반복

승인 게이트를 따로 두지 않는다. PR 리뷰가 게이트고 머지 권한이 사람에게 있다. 멈추거나 갈라지는 건 세 곳뿐이다 — 통합 PR 닫힘(②의 판정), 원인 미특정(②의 절차 4), 배치 상한 초과(②의 절차 2와 5).

반복은 이 스킬 밖의 일이다. `/loop 30m /qa fix`로 얹는다. **`/loop`는 세션에 묶이므로 터미널을 닫으면 멈춘다** — 크론이 아니다. `/schedule`(클라우드 루틴)에는 얹지 못한다: 노션 커넥터가 대화형 인증이라 헤드리스 실행에서 빠지고, 그러면 시트를 못 읽어 스킬이 통째로 죽는다.

## agent가 하지 않는 것

QA를 직접 수행해 항목을 발견하는 일은 사람 몫이다. agent가 볼 수 있는 결함은 스모크 수준이고 그건 CI가 잡는다. UI·UX 결함은 사람 눈이 잡는다 — 그 자리를 자동화가 대신하면 품질이 내려간다.
