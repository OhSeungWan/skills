# tiki-taka

두 팀이 변경·요청을 주고받는 **슬랙 스레드 하나**를 로컬 원장으로 비춰, 사람 기억이 하던 추적을 실측으로 바꾼다. FE 레포에서 돌리든 BE 레포에서 돌리든 절차는 같다 — 원장이 "우리가 어느 쪽인지"를 기억한다. 인자 없이 부르면 sync.

```
슬랙 스레드 (정본)                          대상 레포 (어느 쪽이든)
  BE: "POST /orders에 couponId 추가"        .tiki/ledger.yaml (원장 — 커밋 안 함)
  FE: "errorCode 필드 부탁해요"       ⇄       side·ours: 우리가 누구인지
  BE: "추가했어요"                            items: update·request × ours·theirs
                                              cursor: 마지막으로 소진한 ts
```

## 모델

- **스레드** — 변경·요청이 쌓이는 슬랙 스레드. **정본은 스레드다** — 원장과 어긋나면 스레드가 이긴다.
- **원장** — `.tiki/ledger.yaml`. 스레드를 소스중립 스키마로 비춘 추적 파일. 슬랙 개념은 `thread` URL과 항목 `id`(메시지 ts)에만 스며든다 — 다른 소스가 필요해지는 날 원장은 그대로 두고 읽기·쓰기 절차만 갈아끼운다.
- **우리·상대** — 원장이 사는 레포의 팀이 우리, 스레드 반대편이 상대. `side`는 우리 쪽 라벨(FE, BE, 앱 … 자유 문자열), `ours`는 우리 쪽 작성자 목록이다 — 목록에 없는 작성자는 상대다.
- **항목** — 원장 한 줄. `kind` × `from`으로 네 가지다:

  | | `from: theirs` | `from: ours` |
  |---|---|---|
  | `update` (변경 공지) | 우리 코드에 반영할 것 — `new → applied \| n/a` | 우리가 알린 변경 — `sent` |
  | `request` (요청) | 우리가 답할 것 — `asked → answered` | 상대 응답을 기다리는 것 — `asked → answered` |

- **실측** — 상대 update의 반영 여부를 우리 코드에서 근거를 찾아 판정하는 것. `applied`는 실측으로만 붙는다 — 기억·추정으로 붙이지 않는다.
- **커서** — 마지막으로 소진한 메시지 ts. sync 재실행이 멱등해진다.

```yaml
# .tiki/ledger.yaml — FE 레포의 예. BE 레포의 원장은 같은 스레드를 from만 뒤집어 비춘다.
source: slack
thread: https://<워크스페이스>.slack.com/archives/<채널>/p<스레드ts>
side: FE                              # 우리 쪽 라벨
ours: ["<작성자>"]                     # 우리 쪽 작성자 — 나머지는 상대
cursor: "1724798765.000200"
items:
  - id: "1724712345.000100"          # 소스 메시지 ts
    kind: update
    from: theirs
    summary: "POST /orders 응답에 couponId 추가"
    status: applied                   # theirs: new | applied | n/a · ours: sent
    evidence: "src/api/orders.ts:42"  # applied의 실측 근거
  - id: "1724798765.000200"
    kind: request
    from: ours
    summary: "에러 응답에 errorCode 필드 요청"
    status: asked                     # asked | answered
    answer: ""                        # answered일 때 응답 메시지 ts
```

## 불변식

- `.tiki/`는 커밋하지 않는다 — setup이 `.git/info/exclude`에 등록한다.
- 스레드에 쓰는 행동은 사용자 승인 후에만 한다.
- 조용한 누락 금지 — 잡담으로 건너뛴 메시지도 건수로 보고한다.

## 분류 규칙 (setup·sync 공용)

메시지 하나를 이렇게 소진한다. 작성자가 `ours`에 있으면 `from: ours`, 아니면 `from: theirs`다.

- 변경 공지 → `update` 항목. 상대 것이면 `new`(실측 대상), 우리 것이면 `sent`.
- 요청 → `request`/`asked` 항목. 스킬 밖에서 손으로 올린 메시지도 여기로 흡수된다 — 그래야 중복 검사망에 들어온다.
- 요청에 대한 반대편의 응답 → 해당 항목을 `answered`로, `answer`에 응답 ts. 응답이 변경을 담았으면("추가했어요") 그 메시지로 새 `update` 항목도 만든다 — 상대의 응답이면 실측 루프가 이어받는다.
- 어느 쪽도 아니면 잡담 — 항목 없이 건수만 센다.

## setup — 등록·백필

**언제**: 처음 쓸 때, 스레드를 바꿀 때, 메시지 수정·삭제가 의심될 때(재백필).

1. 스레드 URL을 받고 `slack_read_thread`로 전체를 읽는다.
2. 우리가 어느 쪽인지 확정한다 — 스레드 작성자 목록을 보여주고 `side` 라벨과 `ours`를 사용자에게 확인받는다. 재백필이면 기존 값을 제안한다.
3. 분류 규칙으로 모든 메시지를 소진해 원장을 만든다. 재백필이면 기존 원장의 `evidence`·수동 메모는 같은 id 항목에 승계한다.
4. 상대 `update` 전부 실측한다 — 코드에서 근거를 찾으면 `applied`+`evidence`, 우리 코드와 무관한 변경이면 `n/a`, 못 찾으면 `new`.
5. `cursor`를 마지막 메시지 ts로 놓고 저장한다. `.tiki/`를 `info/exclude`에 등록한다.

**완료 기준**: 스레드의 모든 메시지가 항목이 되었거나 잡담으로 집계되었고, 모든 상대 update에 실측 판정이 붙었을 때.

## sync — 따라잡기 (인자 없으면 이것)

**언제**: 작업 시작 전, "뭐 바뀌었대?", "뭐 요청 왔어?", "이거 적용했었나?".

1. 원장을 읽는다. 없으면 setup부터.
2. 커서 이후 메시지를 읽고 분류 규칙으로 소진한다.
3. `new`인 상대 update 전부 실측한다 — 이전 실행에서 `new`로 남은 것도 포함이다.
4. 커서를 전진시키고 저장한다.
5. 리포트: 미반영 상대 update 표 · 우리가 답할 상대 request 표 · 응답 대기 중인 우리 request 표 · 잡담 N건. **적용·처리는 사용자가 고른 항목만** 진행하고, 반영을 마친 update는 실측 근거와 함께 `applied`로 바꾼다. 상대 request를 처리했으면 tell로 알린다.

**완료 기준**: 커서 이후 메시지가 전부 소진되고, 모든 `new` update에 이번 실행의 실측이 붙었을 때.

## ask·tell — 보내기 (중복 검사 필수)

**언제**: ask — "~한테 요청해줘", 필드 필요, 에러 보고. tell — "변경 공유해줘", 상대가 알아야 할 API·스키마·동작 변경, 상대 request를 처리한 직후.

1. sync를 먼저 돌린다 — 낡은 원장으로 하는 중복 검사는 무의미하다.
2. 보낼 후보를 원장의 우리 항목(ask는 request, tell은 update)·스레드 전문과 대조한다. 같은 취지가 이미 있으면 **그 항목의 상태를 보여주고 멈춘다**.
3. 새 것이면 메시지를 만든다. ask — 어느 API·화면의 맥락인지, 원하는 것, 이유. tell — 무엇이 어떻게 바뀌었는지, 상대가 고칠 것, 어느 request에 대한 답인지. 코드 근거가 있으면 담는다.
4. 사용자 승인을 받고 `slack_send_message`로 스레드에 전송한다.
5. 전송된 메시지 ts를 id로 기록한다 — ask는 `request`/`ours`/`asked`, tell은 `update`/`ours`/`sent`. tell이 상대 request에 대한 답이면 그 항목을 `answered`로, `answer`에 이 ts.

**완료 기준**: 전송된 메시지 ts가 원장 항목으로 기록됐을 때.

## 함정

- **실측은 "반영 안 됨"을 증명하지 못한다** — 근거를 못 찾은 것과 없는 것은 다르다. 판정을 못 내리면 `new`로 두고 리포트에 판정불가로 표기한다.
- 슬랙 메시지 수정·삭제는 커서 뒤라 sync가 보지 못한다 — 스레드와 원장이 어긋나 보이면 setup으로 재백필한다.
- 슬랙 MCP가 안 붙어 있으면 어떤 분기도 시작하지 않는다 — 연결이 필요하다고 안내하고 멈춘다.
- 우리 쪽에 새 사람이 합류하면 `ours`에 추가한다 — 빠져 있으면 그 사람의 요청이 "우리가 답할 것"으로 뒤집혀 쌓인다.
- `side`·`from`이 없는 원장은 구버전(FE 고정)이다 — setup으로 재백필한다.
- 워크트리가 여러 개면 `.tiki/`가 워크트리마다 갈라진다 — 한 스레드를 여러 워크트리에서 추적하면 shared-store 항목으로 등록한다.
- 스레드는 repo당 1개다. 둘째 스레드가 필요해지면 그때 원장을 늘린다.
