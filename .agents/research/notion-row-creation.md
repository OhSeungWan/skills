# 노션 QA DB에 행과 스크린샷 넣기

`design-qa` 스킬(맵 #1, 티켓 #4)이 판정 결과를 노션 QA DB에 행으로 만들 때 부딪히는 실제 제약을 정리한다.
대상 DB의 속성 구성은 티켓 기준으로 테스트 번호(number), 이미지 첨부(**title**), 재현순서(text),
비고(text), 성질(select), 해결 여부(select), PR(url), 테스트한 사람(person)이다.

## 검증 방법과 신뢰도

이 문서의 사실 대부분은 **추론이 아니라 실행 결과**다. 사내 QA DB를 건드리지 않기 위해, 위 속성 구성을
그대로 복제한 **스크래치 데이터베이스를 개인 페이지로 새로 만들어** 거기에 행을 만들고 이미지를 붙이고
쿼리를 돌린 뒤, 검증이 끝나고 휴지통으로 보냈다. SQL 조회 가능 여부만은 워크스페이스에 이미 존재하는
실제 데이터 소스 하나를 **읽기 전용으로** 확인했다.

각 항목에 다음 표시를 달았다.

- **[검증]** — 이 세션에서 실제로 호출해 결과를 확인했다.
- **[문서]** — 도구 스키마나 노션 공식 스펙에 적힌 내용이며, 이번에 직접 실행해 보지는 않았다.

주요 출처는 노션 MCP 도구 스키마(`notion-create-pages`, `notion-create-file-upload`,
`notion-create-attachment`, `notion-update-page`, `notion-query-data-sources`, `notion-fetch`,
`notion-create-database`, `notion-update-data-source`)와, MCP 리소스로 제공되는 노션 공식
마크다운 스펙 `notion://docs/enhanced-markdown-spec`이다.

이 레포는 공개이므로 실제 데이터 소스 id·워크스페이스 URL·사용자 id는 적지 않고 `<data-source-id>`,
`<file-upload-id>`, `<user-id>` 같은 자리표시자로 쓴다.

## 1. 스크린샷 2장을 어디에 붙이나

### 결론

**된다. 링크만 가능한 게 아니라 진짜 이미지 블록이 된다.** 다만 붙는 자리는 **행의 페이지 본문**이지,
행의 속성 칸이 아니다.

### 정확한 호출 순서 (3단계) **[검증]**

로컬 PNG 한 장을 페이지 본문 이미지 블록으로 만들려면 세 번의 왕복이 필요하다.

**1단계 — 업로드 자리를 받는다.** `notion-create-file-upload`에 파일명을 준다. `content_type`은
가능하면 넘기지 않는 게 좋다. 스키마 설명에 따르면 확장자와 어긋나는 MIME 타입을 명시하면 그대로 저장되고
파일이 엉뚱한 종류로 렌더된다.

```json
{ "filename": "shot-real.png" }
```

응답으로 `file_upload_id`, `upload_url`, `upload_headers`, `upload_form_field`(항상 `file`),
그리고 `expires_at`이 온다.

**2단계 — 그 URL로 파일 본체를 직접 POST 한다.** 이건 MCP 도구 호출이 아니라 평범한 HTTP
멀티파트 요청이다. 응답에 담겨 온 `upload_headers`를 전부 그대로 붙이고, 파일을 `file` 폼 필드에 담아
`multipart/form-data`로 한 번 POST 한다. 요청은 정확히 한 번이어야 한다.

성공하면 이런 응답이 온다.

```json
{
  "file_upload_id": "<file-upload-id>",
  "filename": "shot-real.png",
  "content_type": "image/png",
  "content_length": 7853,
  "status": "uploaded",
  "markdown_source": "file-upload://<file-upload-id>",
  "suggested_markdown": "<image src=\"file-upload://<file-upload-id>\"></image>"
}
```

여기서 가장 중요한 사실은 **PNG의 `suggested_markdown`이 `<image>` 태그로 온다**는 것이다.
`<file>`이 아니다. 즉 노션이 스스로 "이건 이미지 블록으로 넣어라"라고 알려준다. `status`가 `uploaded`인지
반드시 확인하고 다음 단계로 넘어간다.

**3단계 — 그 소스를 페이지 본문에 넣는다.** `notion-create-pages`의 `content`(또는
`notion-update-page`)에 위 마크다운을 그대로 쓴다. 두 표기 모두 동작한다.

```markdown
## 실물 (스테이징)

<image src="file-upload://<file-upload-id>">실물 스크린샷</image>

## 시안 (피그마)

![시안 크롭](file-upload://<file-upload-id-2>)
```

**[검증]** 두 표기 모두 진짜 이미지 블록이 됐다. 만든 행을 `notion-fetch`로 다시 읽으면 둘 다
`![캡션](https://prod-files-secure.s3...)` 형태, 즉 노션이 자기 스토리지에 영구 보관한 이미지
블록으로 돌아온다. 파일 링크나 코드 블록으로 떨어지지 않는다.

캡션을 붙일 수 있으므로 **실물 1장과 시안 1장을 캡션으로 구분해 나란히 넣는 것**이 자연스럽다. 스크린샷 2장을
쓰는 이 스킬의 용도에 그대로 맞는다.

### 반드시 알아야 할 제약

**업로드는 1회용이다. [검증]** 한 번 페이지에 붙은 `file_upload_id`를 다른 곳에 다시 쓰면
`File file-upload://<id> not found` 400이 난다. 실물·시안 2장이면 업로드도 2번 따로 해야 한다.

**업로드 URL의 수명은 짧다. [검증]** 응답의 `expires_at`이 발급 시점에서 **약 10분 뒤**로 찍혔다.
1단계와 2단계 사이를 오래 끌면 안 된다. 화면 캡처가 끝난 뒤에 업로드를 시작하는 순서가 안전하다.

**붙이지 않은 업로드는 사라진다. [문서]** `notion-create-attachment` 스키마는 어디에도 붙지 않은
업로드는 임시이며 만료되면 삭제된다고 명시한다. 이 레포의 기존 `grok` 스킬 문서
(`skills/grok/references/notion-assembly.md`)도 첨부가 **약 1시간** 뒤 만료되므로 페이지 생성이
지연됐으면 다시 업로드하라고 적어 두었다. 즉 **업로드하고 나서 곧바로 행을 만들어야 한다.**

**크기 상한. [문서]** 이 단일 파트 업로드 경로는 **20 MiB**까지다. 뷰포트 390 스크린샷은 한참 아래라
문제되지 않는다.

### `files` 속성에는 넣을 수 없었다 **[검증]**

대상 DB의 title 속성 이름이 "이미지 첨부"라서, 별도의 `files` 타입 속성을 만들어 거기에 스크린샷을
꽂는 방법을 시도해 봤다. **이 MCP 경로로는 안 된다.**

`files` 속성을 추가하면 SQLite 스키마에 `"스크린샷" TEXT, -- JSON array of zero or more file IDs`로
잡히지만, 갓 업로드해 `status: uploaded`인 파일을 `["<file-upload-id>"]`(맨 id)와
`["file-upload://<file-upload-id>"]`(URI) **두 형태 모두로 넣어 봤고 둘 다** 400
`File ... not found`로 거절당했다. 여기서 말하는 "file ID"는 MCP 업로드 id와는 다른 무언가로 보인다.

따라서 **스크린샷의 자리는 행의 페이지 본문 하나뿐**이라고 보고 설계하는 게 맞다. 이건 실용적으로 나쁘지
않다. 사람이 노션에서 행을 열면 본문에 실물·시안이 캡션과 함께 세로로 나오고, 이게 시안 대조 QA를 읽는
자연스러운 형태다.

### 참고 — `notion-create-attachment`는 다른 물건이다 **[문서]**

이름이 비슷해 헷갈리지만 용도가 다르다. 이 도구는 세 가지 소스 중 하나를 받는다.

- `content` — UTF-8 텍스트만, 200 KiB 상한. HTML·Markdown·CSV·**SVG** 등. **PNG 같은 바이너리는 못 넣는다.**
- `source_url` — 공개 HTTPS 직링크. 리다이렉트·쿠키·커스텀 헤더·사설 IP 불가. 무료 워크스페이스 5 MiB, 유료 50 MiB.
- `source_file_id` — 같은 인티그레이션이 이미 올린 업로드.

로컬 PNG를 다루는 우리 경우엔 **`notion-create-file-upload` 경로가 맞다.** `create-attachment`는
자기완결 HTML 그림을 `<embed>`로 붙일 때 쓰는 물건이고, 그건 `grok` 스킬이 쓰는 경로다.

## 2. 테스트 번호 채번 — MAX + 1이 유일한 길인가

### MAX + 1은 되기는 한다 **[검증]**

`테스트 번호`가 `number` 타입인 한, 노션은 값을 대신 채워 주지 않는다. 직접 최대값을 읽어 더해야 한다.
SQL 집계는 정상 동작한다.

```sql
SELECT MAX("테스트 번호") AS max_no FROM "collection://<data-source-id>"
```

빈 DB거나 값이 전부 비어 있으면 `MAX`가 `NULL`을 주므로 그 경우 1부터 시작하도록 처리해야 한다.

### 동시 실행에서는 조용히 깨진다

이건 **논리적 결론이며, 실제 경쟁 상태를 인위적으로 만들어 재현하지는 않았다.** 다만 근거는 확실하다.
검증한 범위 안에서 노션 데이터 소스에는 다음이 **전부 없다.**

- number 속성에 대한 unique 제약
- 원자적 증가(atomic increment) 연산
- "읽은 값이 그대로일 때만 쓴다"는 조건부 쓰기(compare-and-set)

따라서 두 실행이 겹치면 둘 다 `MAX`로 N을 읽고, 둘 다 N+1을 쓴다. **에러 없이 중복 번호가 생긴다.**
사람이 시트를 열어 눈으로 발견하기 전까지 아무도 모른다. 재시도로도 못 고친다 — 실패한 게 아니기 때문이다.

### 더 나은 길이 있다 — 노션 네이티브 `UNIQUE_ID` **[검증]**

MAX + 1이 유일한 route가 아니다. 노션에는 **자동 증가 id 속성 타입**이 있고, 이게 정확히 이 문제를
풀라고 있는 물건이다.

`notion-create-database`와 `notion-update-data-source`의 DDL 문법에 `UNIQUE_ID [PREFIX 'X']`가
있다. 기존 DB에 나중에 붙일 수도 있다.

```
ADD COLUMN "자동번호" UNIQUE_ID PREFIX 'QA'
```

검증한 성질은 이렇다.

- 스키마상 타입은 `auto_increment_id`이고, SQLite 상으로는 `INTEGER`로 조회된다.
- **기존 행에 소급 적용된다.** 속성을 추가하기 전에 이미 있던 행이 자동으로 1번을 받았다.
- 새 행에는 값을 주지 않아도 서버가 알아서 다음 번호를 매긴다.
- **값을 직접 쓰려고 하면 거부된다.** 명시적으로 넣으면 400
  `auto_increment_id type is read-only: 자동번호`가 난다.

마지막 성질이 핵심이다. 클라이언트가 번호를 계산하지 않으므로 **경쟁 상태가 원리적으로 성립하지 않는다.**
채번이 서버 한 곳에서만 일어난다.

### 그래서 무엇을 할 것인가

두 가지를 구분해야 한다.

**기존 `테스트 번호`(number)를 `unique_id`로 바꾸는 것은 권하지 않는다.** 타입 변경이 기존 값을
어떻게 처리하는지 검증하지 않았고, 사람이 이미 쌓아 둔 번호가 재배정되면 QA 항목을 번호로 부르던
대화·PR 본문이 전부 어긋난다. 노션에 잘못 건드린 DB는 사람 손으로만 되돌린다.

**현실적인 선택지는 둘이다.**

1. **MAX + 1을 그대로 쓰되, 동시 실행을 설계로 배제한다.** 맵 #1의 확정 제약 12번이 이미
   "트리거는 사람이 슬래시 커맨드"라고 못 박았다. 배포 훅 자동 트리거가 아니므로 두 실행이 겹칠 확률은
   낮다. 이 경우 **중복 번호는 막는 게 아니라 감지해서 보고하는 대상**으로 두는 게 정직하다.
   행을 만들기 직전에 한 번, 만든 직후에 한 번 `MAX`를 읽어 값이 예상과 다르면 리포트에 표기한다.
2. **`UNIQUE_ID` 속성을 새로 하나 추가한다.** 기존 `테스트 번호`는 사람 몫으로 남겨 두고, 에이전트가
   만든 행의 안정적 식별자는 새 자동번호 열이 맡는다. 스키마 변경이 필요하므로 setup에서 사람에게
   동의를 받아야 한다.

**중요한 사실 하나** — 채번 실패는 중복 행과는 다른 문제다. 재실행 중복은 맵 #1의 11번대로 지문 키가
막고, 그건 아래 4번에서 다룬다. 번호가 겹치는 것과 항목이 겹치는 것을 섞지 말 것.

## 3. title 속성에 무엇을 넣을 수 있나

대상 DB의 title 속성 이름은 "이미지 첨부"지만 실제로는 한 줄 요약이 들어가 있다. 이름과 내용이 어긋난
채로 굳은 것이므로, 스킬은 이름이 아니라 **실제 쓰임(한 줄 요약)을 따라야 한다.**

### 마크다운이 살아 있다 **[검증]**

이게 가장 놓치기 쉬운 함정이다. **title은 평문이 아니라 리치 텍스트이고, 인라인 마크다운이 해석된다.**

`홈 히어로 배너 **볼드테스트** 여백이...`를 title로 넣고 다시 읽었더니,

- `notion-fetch`의 `properties`에는 `**볼드테스트**`로 (마크다운 표기로 되돌아옴)
- `notion-fetch`의 `metadata.title`에는 `볼드테스트`로 (별표 없이)
- `notion-query-data-sources`의 SQL 결과에도 `볼드테스트`로 (별표 없이)

나왔다. 즉 `**`가 리터럴로 저장된 게 아니라 **굵게 서식이 실제로 적용됐고**, 평문으로 투영할 때 표기가
사라진 것이다.

**실무적 함의.** QA 요약 문장에는 별표·대괄호·백틱·밑줄이 우연히 섞이기 쉽다. 예를 들어
`[홈] 버튼 *강조* 누락` 같은 문장은 의도와 다르게 렌더된다. 스펙이 명시한 이스케이프 대상 문자는
다음과 같고, 리터럴로 보이고 싶으면 역슬래시를 붙여야 한다.

```
\ * ~ ` $ [ ] < > { } | ^
```

가장 안전한 방침은 **요약문에 서식 문자를 아예 쓰지 않는 것**이다. 화면 이름은 대괄호 대신
`홈 > 히어로` 같은 표기로 쓰면 문제가 사라진다.

### 줄바꿈 **[검증]**

리치 텍스트 속성은 줄바꿈을 담을 수 있고, 다시 읽으면 `<br>`로 돌아온다(재현순서·비고에서 확인).
하지만 **title은 한 줄로 유지해야 한다.** 데이터베이스 표 뷰에서 한 줄만 보이고, 나머지는 잘려 사람이
훑을 때 오히려 방해가 된다.

### 길이 **[문서]**

노션 API의 리치 텍스트 상한은 객체당 **2000자**다. 이번 세션에서 2000자를 넘겨 실제로 거절되는지는
확인하지 않았다. 어차피 한 줄 요약은 그 근처에 갈 일이 없고, **실용 상한은 훨씬 낮다** — 표 뷰에서
읽히려면 한글 40~60자 안쪽이 현실적이다.

### 무엇을 넣을 것인가

이 스킬의 판정 단위는 맵 #1의 8번대로 **섹션 크롭**이다. 따라서 title은 "어느 화면의 어느 섹션이
어떻게 시안과 다른가"를 한 줄로 답해야 하고, 사람이 시트를 훑으며 **본문을 열지 않고도 무슨 항목인지
알 수 있어야** 한다. 앞에 번호를 붙이지 말 것 — 테스트 번호 열이 이미 있다. 지문 키도 넣지 말 것 —
비고에 들어가고, title에 넣으면 사람이 읽는 문장을 기계용 문자열이 오염시킨다.

## 4. 지문 키로 다음 실행에서 걸러낼 수 있나

### 결론 — 된다 **[검증]**

`비고` 같은 text 속성 안의 부분 문자열을 SQL `LIKE`로 찾을 수 있다.

```sql
SELECT url, "테스트 번호", "비고"
FROM "collection://<data-source-id>"
WHERE "비고" LIKE ?
-- params: ["%qa-key: home/hero/spacing%"]
```

이 쿼리로 `qa-key: home/hero/spacing`이 적힌 행을 정확히 찾아냈다. 워크스페이스에 실제로 존재하는
다른 데이터 소스에도 같은 형태의 `LIKE` 쿼리를 **읽기 전용으로** 돌려 정상 실행됨을 확인했다.

`params`로 바인딩하는 파라미터 쿼리를 쓸 것. 화면 이름이나 섹션 이름에 따옴표가 섞여도 안전하고,
도구 스키마도 문자열 보간보다 파라미터를 권한다.

**줄바꿈은 문제가 되지 않는다. [검증]** 비고에 `자동 생성 (design-qa)\nqa-key: home/hero/spacing`처럼
지문 키를 **둘째 줄**에 두고도 `LIKE '%qa-key: ...%'`가 매칭됐다. SQL 결과에서는 줄바꿈이 `\n`으로
돌아온다. 맵 #1의 11번이 말한 "비고 끝에 넣는다"를 그대로 해도 된다.

### 플랜 제약 — 이게 티켓의 핵심 질문이다 **[검증]**

**단일 데이터 소스 SQL은 이 워크스페이스에서 쓸 수 있다. 엔터프라이즈가 아니어도 된다.**

`notion-fetch`에 `self`를 넘기면 현재 플랜에서 각 도구의 접근 상태가 나온다. 이 워크스페이스의
`query_data_sources` 상태는 다음과 같았다.

```
query_data_sources: available_with_limit
```

`upgrade_required`가 아니라 `available_with_limit`이다. 도구 스키마의 설명과 맞춰 읽으면 그림이
분명해진다.

| 모드 | 가용성 |
|---|---|
| **뷰 모드** | 모든 플랜에서 도구별 쿼터 없이 사용 가능 |
| **단일 데이터 소스 SQL** | Business·Enterprise(+Notion AI)는 무제한. **그 외 플랜은 워크스페이스 공용 사용량 한도 안에서 사용 가능** |
| **다중 데이터 소스 SQL** | **Enterprise + Notion AI 필요** |

우리가 필요한 건 **QA DB 한 장에 대한 단일 데이터 소스 SQL**이다. 여러 데이터 소스를 조인할 일이
없으므로 **엔터프라이즈 제약에 걸리지 않는다.** 다만 "무제한"도 아니다. 공용 사용량 한도가 있으므로
**실행당 쿼리 수를 아껴야 한다.**

실용적으로는 이렇게 하면 된다. 지문 키를 하나씩 N번 조회하지 말고, **실행 시작 시점에 한 번**
기존 키를 통째로 읽어 메모리에 올린 뒤 클라이언트에서 대조한다.

```sql
SELECT "비고" FROM "collection://<data-source-id>" WHERE "비고" LIKE '%qa-key:%'
```

쿼리 1회로 끝나고, 채번용 `MAX` 조회와 합쳐도 실행당 2회다.

**한도에 걸렸을 때의 폴백 [문서]** — 뷰 모드는 모든 플랜에서 쿼터 없이 쓸 수 있다. `notion-fetch`로
얻은 뷰 URL로 행을 페이지네이션해 읽고 클라이언트에서 필터링하면 SQL 없이도 같은 일을 할 수 있다.
느리지만 막히지는 않는다. 이 폴백을 스킬에 적어 두는 게 좋다 — 공용 한도는 다른 사람의 사용량으로도
소진될 수 있어서, 우리 잘못 없이 갑자기 실패할 수 있다.

### 키 설계에서 주의할 점

`LIKE '%...%'`는 **부분 문자열 매칭이라 접두어 충돌이 난다.** `qa-key: home/hero/spacing`은
`qa-key: home/hero/spacing-2`에도 매칭된다. 카테고리 이름이 서로의 접두어가 되는 순간 새 항목이
기존 항목으로 오인돼 **조용히 누락된다** — 맵 #1의 14번이 경계하는 바로 그 실패 양상이다.

해결은 간단하다. 키를 **끝 경계가 분명한 형태로 감싼다.**

```
qa-key: [home/hero/spacing]
```

이러면 `LIKE '%qa-key: [home/hero/spacing]%'`가 접두어 충돌 없이 정확히 매칭된다. 다만 대괄호는
위 3번에서 본 이스케이프 대상 문자다. 비고는 title만큼 서식이 민감하진 않지만, 대괄호가 걱정되면
줄 끝 개행을 경계로 삼거나 `qa-key: home/hero/spacing;`처럼 세미콜론으로 닫아도 된다.

## 5. 에이전트가 만든 행임을 표시할 자리

### person 속성은 진짜 사용자 id를 요구한다 **[검증]**

`테스트한 사람`은 person 타입이고, SQLite 스키마에
`"테스트한 사람" TEXT, -- JSON array of zero or more user IDs`로 잡힌다.

**쓰기는 된다.** 실제 워크스페이스 사용자 id 하나를 배열로 넣어 행을 만들었고 정상 저장됐다.
다시 읽으면 `["<mention-user url=\"user://<user-id>\"></mention-user>"]` 형태로 돌아온다.

문제는 **넣을 만한 봇 계정이 없다**는 것이다. `notion-get-users`로 워크스페이스 사용자를 조회하면
사람 계정만 나오고, MCP 인티그레이션 자신은 person 목록에 나타나지 않는다(업로드 토큰 안에는 `botId`가
들어 있으므로 봇으로서 존재하기는 한다). 즉 **인티그레이션을 `테스트한 사람`에 넣을 수단이 없다.**

**따라서 `테스트한 사람`은 비워 두는 게 맞다.** 사람 id를 아무거나 넣으면 그 사람이 QA를 한 것처럼
보여서 명백히 틀린 기록이 된다. 이건 단순한 빈칸이 아니라 **정직한 빈칸**이다 — 사람이 테스트하지
않았으므로 사람 이름이 없는 게 사실이다.

### 표시할 자리 — 선택지 세 가지

**(1) checkbox 속성을 새로 추가한다. [검증]** 가장 깔끔하다.

```
ADD COLUMN "에이전트 생성" CHECKBOX
```

값은 `"__YES__"` / `"__NO__"`로 쓴다. 행 생성 시 `"에이전트 생성": "__YES__"`로 넣어 정상 저장됐고,
SQL로도 조회된다. 사람이 노션에서 **체크박스 하나로 필터링**할 수 있다는 게 큰 장점이다 —
"에이전트가 만든 것만 보기" 뷰를 사람이 직접 만들 수 있다. 스키마 변경이 필요하므로 setup에서 동의를 받아야 한다.

**(2) 비고에 표식을 함께 적는다. [검증]** 스키마를 안 건드려도 된다. 이미 지문 키를 비고에 넣으므로
같은 자리에 한 줄 더 붙이면 된다.

```
자동 생성 (design-qa)
qa-key: home/hero/spacing
```

`LIKE '%자동 생성 (design-qa)%'`로 조회도 된다. 다만 사람이 시트에서 필터를 걸기엔 (1)보다 번거롭다.

**(3) 페이지 아이콘. [문서]** `notion-create-pages`가 `icon`을 받으므로 `🤖` 같은 이모지를 주면
행 목록에서 눈에 띈다. 필터링은 안 되지만 시각적 구분으로는 가장 저렴하다. (1)·(2)와 같이 써도 된다.

### 권고

**(2)를 기본으로, (1)을 setup 옵션으로 둔다.** 지문 키를 어차피 비고에 쓰므로 (2)는 추가 비용이
0이고 스키마 변경도 없다. 사람이 "에이전트가 만든 행만 따로 보고 싶다"고 하면 그때 (1)을 추가하면 된다.
아무 표식도 없이 사람 항목과 섞이는 것만은 피해야 한다 — 시트가 병목이라는 게 이 스킬의 전제인데,
출처를 모르는 행이 쌓이면 사람이 시트를 신뢰하지 않게 된다.

## 한 행을 만드는 전체 흐름

지금까지의 사실을 하나로 합치면 실행 1건은 이렇게 흐른다.

1. **기존 지문 키를 한 번에 읽는다** — `SELECT "비고" ... WHERE "비고" LIKE '%qa-key:%'` (쿼리 1회)
2. **채번을 위해 최대값을 읽는다** — `SELECT MAX("테스트 번호") ...` (쿼리 1회)
3. **새로 발견한 불일치만 남긴다** — 1단계 결과에 이미 있는 키는 버린다
4. **남은 항목마다 스크린샷 2장을 업로드한다** — 항목당 `create-file-upload` 2회 + HTTP POST 2회.
   업로드 URL이 10분 안에 만료되므로 여기서 지체하지 않는다
5. **행을 만든다** — `notion-create-pages` 한 번에 여러 페이지를 넘길 수 있다(최대 100).
   속성에 title 한 줄 요약·테스트 번호·성질 `폴리싱`·해결 여부 `시작전`·비고(지문 키 + 자동 생성 표식)를
   넣고, `content`에 `<image src="file-upload://...">` 2장을 캡션과 함께 넣는다.
   `테스트한 사람`은 비워 둔다
6. **리포트한다** — 만든 행 수, 지문 키로 걸러낸 중복 수, 미커버 프레임 수(맵 #1의 14번)

한 실행에서 SQL 쿼리는 2회면 충분하다. 공용 사용량 한도가 있는 플랜이므로 이 숫자를 지키는 게 좋다.

## 열린 것 / 확인하지 못한 것

정직하게 남겨 둔다.

- **title 2000자 상한을 실제로 넘겨 보지 않았다.** 문서상의 값이고, 한 줄 요약에는 영향이 없다.
- **동시 실행 경쟁 상태를 인위적으로 재현하지 않았다.** unique 제약·원자적 증가·조건부 쓰기가 없다는
  관측에서 나온 결론이다.
- **`number` → `unique_id` 타입 변경이 기존 값을 어떻게 처리하는지 검증하지 않았다.** 위험해서 시도하지
  않았다. 필요하면 사본에서 먼저 확인할 것.
- **`files` 속성이 요구하는 "file ID"의 정체를 못 밝혔다.** MCP 업로드 id는 아니다. 노션 UI로 올린
  파일에는 다른 식별자가 있을 수 있다. 지금 설계에는 필요 없어서 더 파지 않았다.
- **대상 QA DB의 실제 스키마를 직접 읽지 않았다.** 티켓에 적힌 속성 구성을 복제한 스크래치 DB로
  검증했다. 특히 **`해결 여부`의 타입을 확인해야 한다** — 티켓은 `select`라고 적었지만, 이 레포의
  기존 `qa` 스킬 초안은 같은 속성을 `status` 타입에 7개 상태로 설계해 두었다. `select`와 `status`는
  타입이 달라 쓰는 방법도 다르므로, **스킬을 쓰기 전에 실제 DB에서 어느 쪽인지 확인해야 한다.**
